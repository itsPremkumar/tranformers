# 🤖 Complete Jetson + ESP32 System Architecture & Design Specifications
> **Omni-Morph Transformer Humanoid Upgrade - Version 3.0**

This document serves as the master engineering specification for migrating the Omni-Morph Robot from an isolated network/laptop-tethered system to a fully onboard, accelerated edge platform using an **NVIDIA Jetson** processor alongside the existing **ESP32** controllers.

---

## 1. Complete System Architecture

The robot employs a **Hierarchical Distributed Control Topology**. High-level cognitive features are running in real-time on the onboard NVIDIA Jetson GPU compute block, while low-level real-time actuation, balance correction, safety systems, and sensor acquisitions run on the dual-core ESP32 microcontrollers.

```
       [ Local User / Cloud WebRTC Portal ]
                        │
                        ▼ (Wi-Fi / WebSockets / gRPC)
       [ NVIDIA Jetson Orin Onboard Computer ]
     ┌──────────────────┴──────────────────┐
     ▼ (CUDA Core GPU)                     ▼ (CPU Core Runtimes)
 [ Isaac ROS Vision / SLAM ]         [ Local LLM / speech Pipeline ]
     │                                     │
     └──────────────────┬──────────────────┘
                        ▼ (ROS 2 Humble / Topics & Actions)
         [ ROS 2 Hardware Bridge Node ]
                        │
                        ▼ (USB-to-UART / CAN Bus 500kbps)
         [ ESP32 Motion Controller ]
     ┌──────────────────┴──────────────────┐
     ▼                                     ▼
 [ PCA9685 Servo Drivers ]            [ L298N DC Motors ]
 (18 DOF S-Curve Smoothing)           (Yaw Straight-Drive Assist)
```

### Subsystem Division of Labor
*   **Jetson Cognitive Layer:** Operates as the "Master." Runs ROS 2 Humble over Ubuntu 22.04 LTS. Handles CPU-intensive workloads: Voice interaction (Whisper/Piper), Visual SLAM (Isaac ROS), Object detection (YOLOv8/TensorRT), Gesture detection, local LLM mission planning (llama.cpp/Ollama), and Cloud Telemetry.
*   **ESP32 Physical Layer:** Operates as the "Servant." Runs bare-metal C++ with FreeRTOS. Responsible for low-latency physical loops: S-curve joint trajectories, IMU pitch/roll balance, ultrasonic scanning, H-bridge current limit overrides, and emergency stop interlocks.

                            [ Respeaker Mic]                                       ├─► [ PCA9685 Servo Driver ] ──► [ 18x Servos ]

### Power Delivery & Safety Isolation
*   **Primary Power Source:** 2S LiPo battery supplying 7.4V (nominal) to 8.4V (fully charged).
*   **Jetson Power Path:** Routed through a **QS-1212CCBA-80W Buck Converter** regulated to **5.1V at 6A** peak. Connects directly to the barrel jack of the Jetson. The J48 jumper is closed to disable micro-USB power, preventing power throttling or brownouts during GPU inference spikes.
*   **ESP32 Power Path:** Isolated through a separate **5V at 3A Buck Converter** connected to the ESP32 VIN pin. Isolating the power rail protects the microcontrollers from electromagnetic noise generated by the Jetson GPU or DC motor spikes.
*   **Emergency Stop Relay:** A hardware normally-closed (NC) relay is wired in series with the high-current servo power supply. Triggered instantly by the ESP32 safety GPIO if battery falls below 6.0V or motor current spikes above 3.0A.

### Onboard Sensors & Actuators
*   **Cameras:** Intel RealSense D435i depth camera connected over USB 3.0 (for Visual SLAM and obstacle pointclouds) and Sony IMX219 CSI wide-angle camera (for face/gesture tracking).
*   **Lidar:** RPLIDAR A1/A2 scanning 360 degrees for 2D safety bubble and localization mapping.
*   **Audio Input/Output:** ReSpeaker 4-Mic Array (USB) for directional wake-word localization, and MAX98357A I2S Amplifier connected to Jetson I2S pins for local audio voice synthesis.
*   **Inertial Measurement:** MPU6050 IMU communicating with ESP32 via I2C at 400kHz.
*   **Servo Controller:** PCA9685 16-channel PWM driver communicating with ESP32 over a secondary isolated I2C bus.

## 3. Communication Architecture

The communication system uses specialized protocols matching the latency and bandwidth requirements of each layer.

| Link Path | Hardware Interface | Software Protocol | Key Message Data | Target Latency |
| :--- | :--- | :--- | :--- | :--- |
| **Jetson ↔ ESP32** | USB-to-TTL (CP2102) / CAN | UART (115200) / SocketCAN | Velocity `/cmd_vel`, IMU data, battery metrics, triggers | < 10ms |
| **Intra-Jetson Nodes** | Shared RAM / GPU Memory | ROS 2 DDS (CycloneDDS / SharedMem) | Camera frames, pointclouds, TF frames | < 1ms (Zero-Copy) |
| **Jetson ↔ Local LLM** | Unix Socket | REST API / HTTP | JSON chat prompt queries and text streams | < 5ms |
| **Swarm ↔ Peer Robots** | Wi-Fi / ESP-NOW | WebSockets / UDP Broadcast | Shared coordinate maps, diagnostic alerts | < 50ms |
| **Jetson ↔ Cloud** | 4G LTE / Wi-Fi | MQTT / WebRTC | Telemetry payloads, OTA binaries, video streams | < 200ms |

### Subsystem Bridge Implementation
1.  **UART Serial Link (Standard Setup):** Maps `/dev/ttyRobotMotion` on Jetson to Hardware Serial2 (GPIO 16/17) on the ESP32. Commands are newline-terminated strings (e.g. `CMD:FORWARD\n`).
2.  **CAN Bus Link (Industrial Setup):** Utilizes native Jetson MTTCAN SocketCAN driver (`can0`) bridged to a Waveshare SN65HVD230 transceiver. On the ESP32, an MCP2515 SPI module converts frames. Data packets are packed as binary struct schemas for minimal parsing overhead.

## 4. AI Architecture

```
[ Wake Word (Porcupine) ] ──► [ STT (Whisper.cpp) ] ──► [ LLM (Ollama / Llama 3) ] ──► [ TTS (Piper) ]
                                                                │
                                                                ▼
                                                      [ Mission Planner / BT ]
                                                      (Command: CMD:TRANSFORM)
```

*   **Wake Word Detection:** Runs local `Porcupine` or `Snowboy` engine monitoring the ReSpeaker mic array.
*   **Speech-to-Text (STT):** Local `whisper.cpp` container. Converts voice input to text utilizing the Whisper-Base model optimized with CUDA.
*   **Local LLM Reasoning:** Runs quantized GGUF models (`Llama-3-8B-Instruct-GGUF` or `Phi-3-Medium-GGUF`) inside an Ollama container. Evaluates natural language queries and outputs formatted system commands.
*   **Semantic RAG Vault:** Incorporates a local ChromaDB vector database. User input is embedded using `all-MiniLM-L6-v2` to query relevant historical facts or technical specifications, feeding it as context to the LLM.
*   **Mission Planning & Behavior Trees:** Parses LLM commands and runs execution loops inside BehaviorTree.CPP, prioritizing safety sequences (obstacle distance) over user directions.

## 5. Computer Vision Architecture

The perception pipeline is accelerated on the Jetson Orin GPU using **NVIDIA Isaac ROS** to prevent CPU bottlenecks.

```
[ CSI / Realsense Cam ] ──(NVMM GPU Memory)──► [ Isaac ROS DNN / TensorRT ] ──► [ Target Coordinates ]
         │                                              │
         ▼                                              ▼
[ Isaac ROS Visual SLAM ] ─────────────────────► [ local Costmap ] ──► [ Nav2 Path Finder ]
```

*   **Zero-Copy Frame Processing:** Argus CSI camera plugin outputs raw frame arrays directly to Jetson GPU Memory (`NVMM`). Avoids CPU copies.
*   **Object Detection:** Runs YOLOv8 models optimized via **TensorRT** inside the `isaac_ros_dnn_inference` pipeline. Outputs 2D bounding boxes and 3D pose estimations of targets.
*   **Visual SLAM:** Utilizes **Isaac ROS Visual Odometry** (`isaac_ros_visual_slam`) parsing depth frames from the Intel RealSense D435i. Publishes high-frequency `/odom` transforms.
*   **Reconstruction & Obstacle Avoidance:** Runs **Isaac ROS Nvblox** (`isaac_ros_nvblox`) to process depth images and build a local Euclidean Signed Distance Field (ESDF), publishing local costmaps to Nav2.

## 6. Robotics Middleware Architecture

The ROS 2 Humble layout encapsulates the robot's capabilities into modular nodes.

### Node Structure

```
  ┌─────────────────────────────────────────────────────────────────┐
  │                           ROS 2 Nodes                           │
  ├───────────────────────┬─────────────────────────────────────────┤
  │ Node Name             │ Description                             │
  ├───────────────────────┼─────────────────────────────────────────┤
  │ /serial_bridge_node   │ Serial interface translating to ESP32   │
  │ /face_tracker_node    │ Visual face tracker (head PAN/TILT)     │
  │ /gesture_detector     │ Hand gesture interpreter (Twist output) │
  │ /llm_agent_node       │ Local LLM prompt reasoning coordinator  │
  │ /behavior_tree_node   │ Main autonomous executive logic        │
  │ /health_monitor_node  │ Diagnostic aggregator and alerts         │
  └───────────────────────┴─────────────────────────────────────────┘
```

### Core Communication Topics
*   `/cmd_vel` (`geometry_msgs/msg/Twist`): Target linear and angular velocities.
*   `/cmd_transform` (`std_msgs/msg/String`): Initiates transformation sequence ("TRANSFORM").
*   `/head/pan` & `/head/tilt` (`std_msgs/msg/Int32`): Coordinates head gimbal angles.
*   `/sensor/ultrasonic` (`sensor_msgs/msg/Range`): Distance to obstacles.
*   `/sensor/battery` (`robot_interfaces/msg/BatteryState`): Battery voltage, current, and charge indicators.
*   `/imu/data_custom` (`robot_interfaces/msg/IMUData`): Roll, pitch, yaw, and raw accelerations.
*   `/diagnostics` (`diagnostic_msgs/msg/DiagnosticArray`): Node status health reports.

### Service Definitions
*   `/robot/trigger_transformation` (`robot_interfaces/srv/TriggerTransformation`): Requests state changes.
*   `/robot/calibrate_servos` (`robot_interfaces/srv/CalibrateServos`): Modifies active joint offsets.

## 7. Motion Control Architecture

*   **ESP32 Actuator Engine:** Preserves existing dual-core FreeRTOS C++ loops. The PCA9685 registers S-Curve velocity curves to smooth transitions, protecting physical servos from back-EMF spikes.
*   **Gyro Yaw Assist:** The ESP32 continuously polls the MPU6050. When walking or driving, it applies differential power adjustments to left/right motors to prevent drift.
*   **High-Level Transformation Planner:** The Jetson coordinate server maps joint limits before transformation. If `/robot/trigger_transformation` is called, it verifies that the robot is stationary, lowers the center of gravity, sends the serial trigger, and locks navigation inputs until the ESP32 reports completion.

## 8. Autonomous Navigation Architecture

The navigation stack integrates Nav2 with Isaac ROS.

```
[ RPLIDAR / Depth Cam ] ──► [ RTAB-Map / SLAM ] ──► [ Occupancy Grid Map ]
                                    │
                                    ▼
[ Current Pose ] ─────────────► [ Nav2 Planner ] ──► [ Path Sequence ] ──► [ /cmd_vel Bridge ]
```

*   **SLAM Mapping:** Runs RTAB-Map or Isaac ROS SLAM. Saves a permanent 3D octomap and 2D occupancy grid to the Jetson storage.
*   **Path Planning:** Nav2 consumes the occupancy grid and utilizes the Smac Planner to compute kinematically feasible trajectories for the robot's current mode (Humanoid walking envelope vs. Car driving footprint).
*   **Obstacle Avoidance:** Local costmaps update at 20Hz. If a dynamic obstacle enters the local safety bubble, the recovery server triggers a pivot or stop command.

## 9. Voice Interaction Architecture

*   **Wakeword Listener:** Node runs constantly, listening to index 0 of the audio input interface. If "Omni" is detected, it triggers the SSD1306 face to display `CMD:OLED_THINK` and starts recording.
*   **Transcription:** Captures raw audio for 3 seconds, runs Whisper local inference, and publishes the resulting text to `/voice/user_speech`.
*   **Reasoning:** `llm_agent_node` processes the transcript and publishes verbal response strings to `/speech/speak`.
*   **Voice Synthesis:** Piper TTS generates raw PCM audio. This is streamed directly to the local MAX98357A amplifier while forwarding a `lip_sync` flag to trigger physical head servo sweeps and SSD1306 mouth animations.

## 10. Cloud Architecture

*   **Telemetry Stream:** A lightweight Python MQTT client bridges local ROS topics to AWS IoT Core over an encrypted TLS connection. Streams battery levels, diagnostics, and current coordinates at 1Hz.
*   **WebRTC Video Tunnel:** GStreamer captures the CSI camera feed and encodes it as H.264, streaming it via a WebRTC signaling server (using Janus or Kinesis Video Streams) to permit low-latency remote pilot control.
*   **Remote OTA Updates:** An onboard OTA service downloads system updates (`docker-compose.yml` or ESP32 firmware binaries) from an authenticated S3 bucket, executes security signature verification, and invokes the local platformio builder to flash the ESP32.

## 11. Debugging Architecture

```
[ ROS 2 Diagnostic Updater ] ──► [ /diagnostics Topic ] ──► [ Foxglove Studio Dashboard ]
                                          │
                                          ▼
[ CPU/GPU / Thermal Sensors ] ──────► [ jtop / jtop_bridge ] ──► [ Prometheus / Grafana ]
```

*   **System Diagnostics:** Every ROS 2 node implements `diagnostic_updater::Updater` to report heartbeat, frame drops, serial reconnect counts, and memory footprints.
*   **Visual Debugger:** Connects to **Foxglove Studio** over a WebSocket bridge (`ros-humble-foxglove-bridge`). Enables real-time remote plotting of camera streams, TF trees, and URDF joint models.
*   **Compute Monitoring:** Runs Prometheus on the Jetson to scrape system metrics (CPU/GPU utilization, thermal zones, power consumption via `jtop`). Metrics are visualized in a local Grafana dashboard.

## 12. Security Architecture

*   **Encrypted DDS:** FastDDS is configured with security plugins enabled. ROS 2 node communication is encrypted using S/MIME certificates to prevent interception on local Wi-Fi networks.
*   **Device Isolation:** UFW firewall rules on the Jetson block all incoming network connections except port 22 (SSH, key-based authentication only), port 80 (local Nginx proxy), and port 8765 (Foxglove bridge).
*   **Firmware Verification:** ESP32 OTA binaries are signed using private RSA keys. The ESP32 bootloader verifies the signature before flashing to prevent execution of unauthorized code.

---

## 13. Deployment Architecture

*   **Docker Containerization:** Isolates modules. ROS 2 dependencies and Isaac ROS nodes run inside a container equipped with GPU passthrough capabilities. Ollama runs in a parallel container.
*   **CI/CD Automation:** GitHub Actions pipeline triggers on pushes to the `main` branch. Executes python linter checks, compiles the ROS 2 workspace, builds Docker images for ARM64 using QEMU, and pushes completed builds to the GitHub Container Registry.
*   **Rollback Strategy:** The Jetson runs double partition boot setups (A/B layout). If an OTA kernel update fails to boot, it falls back to the previous stable state partition.

## 15. Development Workflow

```
[ Write Code Local PC ] ──► [ auto_sync_jetson.py ] ──► [ SSH Wireless Sync ] ──► [ Auto-Restart Container ]
          │                                                                                 ▲
          └───────────────► [ Sim & Test (Isaac Sim) ] ──► [ Git Commit & CI Build ] ───────┘
```

1.  **Local Workspace Development:**
    Developers write ROS 2 Python/C++ code on a local workstation. Code formatters and linters (`black`, `flake8`, `cpplint`) are executed to maintain standards.
2.  **Wireless Code Synchronization (Direct Upload):**
    For rapid testing without hitting GitHub, the developer runs the custom autodiscovery script [auto_sync_jetson.py](file:///c:/one/tranformers/robot_project/tools/auto_sync_jetson.py) on their PC:
    *   **Autodiscovery:** Scans the subnet and resolves the Jetson via mDNS (`jetson.local`) or parallel port scans (looking for active hosts with SSH port 22 open).
    *   **Auto-Sync:** Caches the found IP and uses `rsync` or `scp` to recursively upload the local workspace directory directly to the Jetson (`~/robot_project`) wirelessly.
    *   **Auto-Deployment:** Wirelessly triggers the Jetson's build and compose script (`run_all.sh`) to automatically compile and reload the containerized ROS 2 nodes.
3.  **Simulation & Validation (Isaac Sim):**
    Robot URDF models are loaded into **NVIDIA Isaac Sim** on a GPU-enabled desktop. Perception algorithms (Visual SLAM, object tracking) are verified against simulated cameras. Navigation velocity commands are mapped to simulated motor responses.
4.  **HIL Integration Testing & Production Deployment:**
    Code is pushed to the staging/main branch, triggering the CI/CD pipeline to build the multi-stage Docker containers. Once built, the container is tagged as `stable`. The production robot node pulls the container from the GitHub Container Registry, runs `docker-compose up -d`, and logs performance metrics.
5.  **Production Maintenance:**
    The system diagnostics node publishes health updates to Grafana. If a node crashes, the Docker daemon automatically executes a container restart while logging the stack trace to Sentry.
